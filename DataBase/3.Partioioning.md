# Database Partitioning: Revision Notes

Source: AlgoMaster.io, System Design course (Database Scaling Techniques). Notes are condensed and in my own words.

---

## 1. The problem it solves

A single table that grows to hundreds of millions or billions of rows causes:

- Large indexes that eat memory and disk
- Queries scanning far more data than needed
- Slow, expensive deletes and archiving
- Longer backups and maintenance

## 2. What is partitioning?

- Split **one logical table** into several **smaller physical pieces** (partitions).
- The app still queries one table name. The database routes each row to the right partition.
- Usually lives on **one database server**.

## 3. Horizontal vs vertical

| | Horizontal | Vertical |
|---|---|---|
| Splits | Rows | Columns |
| Each piece has | All columns, some rows | All rows, some columns |
| Example | Orders split by year | Rarely used big column moved to a separate table |

"Partitioning" in system design almost always means **horizontal**.

## 4. The three strategies

| | Range | List | Hash |
|---|---|---|---|
| Assigned by | Value range | Explicit list of values | Hash of the key |
| Typical key | Date, numeric ID | Region, country, category | user_id, customer_id |
| Keeps related values together | Yes | Yes | **No** |
| Even distribution | Depends on data | Depends on data | Usually even |
| Best for | Time-series, range queries | Few known categories | Spreading load evenly |

**Range**
- Lower bound inclusive, upper bound exclusive (midnight Feb 1 goes to the February partition).
- Great for "last week" or "March" style queries and for time-series data.

**List**
- One partition can cover several values (e.g. many countries in "Europe").
- A catch-all partition handles unlisted values.
- Risk: skewed categories (one region holding 80% of rows) defeat the purpose.

**Hash**
- Neighbouring keys (1000, 1001) land in different partitions.
- Range queries must check **all** partitions.
- Choose it when even spread matters more than locality.

## 5. Partition pruning (the main performance win)

- If the query filters on the **partition key**, the database skips partitions that cannot match.
- Example: 5 years of monthly partitions = 60. A query for September 2026 reads **1 of 60**.
- If the query filters on a different column, **no pruning**: all partitions are checked.

## 6. Choosing the partition key

- Match the key to the **most common query's WHERE clause**, not to the table.
- Example: events table, query "last 24 hours".
  - Partition by `created_at`: reads 1-2 partitions.
  - Partition by `user_id`: recent events are spread across every partition, so reads all of them.
- If the common query were "all events for user 42", `user_id` would be the better key.

## 7. Partitioning + indexes

- They work together, at different levels.
- Query for customer 42 in September: prune to the September partition, then use that partition's `customer_id` index.
- Per-partition indexes are smaller and more likely to fit in memory.
- **Constraint:** in some databases (e.g. PostgreSQL), a primary key or unique constraint on a partitioned table **must include the partition key**, because uniqueness is only checked within a partition.

## 8. Data lifecycle benefits

- Deleting old data with a big `DELETE` is slow: row-by-row work, heavy logging, dead space left behind.
- With partitions, **drop or detach the whole partition**. It removes files, so cost does not depend on row count.
- A detached partition can be archived, moved to cheaper storage, exported to a warehouse, or kept read-only.

## 9. Maintenance benefits

- Rebuild indexes one partition at a time.
- Collect statistics per partition (analyze busy recent ones more often).
- Back up old, unchanging partitions once.
- Leave cold data alone, focus on active partitions.
- Works best for **append-heavy** data: logs, events, transactions, time-series.

## 10. Pitfalls

**Uneven partitions**
- One partition holding 95%+ of the data behaves almost like the original table.
- Fix: choose boundaries from the real data distribution, and sub-partition big ones (e.g. by country or hash of user ID).

**Too many partitions**
- Example: partitioning by minute gives about 525,600 partitions a year.
- Costs: metadata overhead, slower query planning, operational work to create and clean up partitions, tiny partitions with no real benefit.

Rule of thumb for granularity:

| Granularity | Partitions/year | Fits |
|---|---|---|
| Hourly | 8,760 | Very high-volume events/metrics |
| Daily | 365 | High-volume logs, short retention |
| Monthly | 12 | Orders, transactions, moderate logs |
| Yearly | 1 | Low volume, long retention |

Sanity check: if the common query is "last 7 days", daily partitions mean 7 reads, hourly would mean 168 for no extra benefit.

## 11. Partitioning vs sharding

| | Partitioning | Sharding |
|---|---|---|
| Where pieces live | Usually one server | Multiple servers |
| Who routes queries | The database | App, proxy, or routing layer |
| Main benefit | Faster queries, easier data management | Scales storage and write capacity past one machine |
| Adds CPU/RAM/disk? | No | Yes |
| Downsides | Design work, key constraints | Cross-server queries, distributed coordination |

- Often **combined**: shard users across servers, then partition each shard's tables (e.g. events by month).

## 12. When to use it

Ask these four questions:

1. Is the table large enough to actually cause problems?
2. Do common queries filter on a natural partition key?
3. Will pruning eliminate a meaningful share of data?
4. Will it make maintenance or retention easier?

- Mostly yes: partitioning likely helps.
- Mostly no: try better indexes or query tuning first. Small tables (a few million rows with good indexes) usually do not need it.

---

## Quick-recall cheat sheet

- Partitioning = split one table into pieces, usually on **one server**. Sharding = pieces on **many servers**.
- Horizontal = rows. Vertical = columns.
- Range for time, list for categories, hash for even spread.
- Pruning only works when the query filters on the **partition key**.
- Pick the key from **query patterns**.
- Drop a partition instead of running a huge DELETE.
- Avoid skewed partitions and avoid too many tiny partitions.
- Unique keys on partitioned tables usually must include the partition key.
